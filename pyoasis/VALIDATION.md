# Validation

## Validation objective

The publication-oriented KOH2 pyOASIS wrapper was checked against the
previously used operational processing workflow to verify that the refactoring
did not change the final TEC product.

## Representative validation case

```text
Station : KOH2
Date    : 2025-01-01
DOY     : 001
```

The test used the same observation data, orbit-product workflow and pyOASIS
processing sequence as the operational processing.

The final product checked was:

```text
KOH2_001_2025_L1L2.TEC
```

located under:

```text
pyOASIS_OUTPUT/INDICES/TEC/
```

## Processing chain checked

```text
observation RINEX
-> GFZRNX RINEX 2.x staging
-> GFZ MGEX rapid SP3
-> SP3intp
-> RNXclean
-> RNXlevelling
-> ROTIcalc
-> DTECcalc
-> SIDXcalc
-> TECcalc
-> final L1/L2 TEC product
```

## Bit-for-bit equivalence

The final TEC product from the publication wrapper was compared with the
corresponding operational result using SHA-256.

Both files produced:

```text
4280d8a6451adc158cb0b37f350f5b67ef45482587d57e6f6b7096dcfac5634f
```

Therefore the representative final TEC output is bit-for-bit identical.

## Validation conclusion

For KOH2 on 2025-01-01, the publication-oriented pyOASIS workflow reproduces
the operational final TEC product exactly.

This establishes representative wrapper-equivalence for the publication
refactor.

It does **not** mean that every processed KOH2 day from 2019-2026 was
independently checksum-validated.

## Relationship to later validation analyses

The pyOASIS TEC products generated by this workflow are subsequently evaluated
in the separate analysis workflows, including comparison with IGS Final GIM
and Madrigal products. Those external comparison results belong in the
corresponding analysis directories rather than in this processing validation
record.
